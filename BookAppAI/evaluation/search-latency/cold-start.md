# 갈피 재시작 직후 첫 추천 · 2026-11-28

운영 PR #43 배포 직후 첫 작업은 Spring의 AI 응답 제한 60초를 넘겼다. AI의 처리 시간 70.19초 중 기존 로그가 ‘후보 준비’로 집계한 구간이 46.28초였다. 인덱스 준비는 13.81초, 임베딩은 4.00초, Gemini 순위 결정은 2.29초였다. 같은 질문을 다시 실행한 두 작업은 책 2권을 반환했다.

## 재현 조건

기준 커밋은 `58d3dc8`이다. 격리된 로컬 Docker 환경에서 Spring, AI, 라우터, PostgreSQL, Redis가 CPU 2개와 메모리 952MiB를 공유했다. AI 컨테이너 메모리 상한은 192MiB였다. 도서 176권의 합성 필드·태그·768차원 벡터를 사용했고 두 코드 버전 각각의 식별자에만 유효한 테스트 픽스처로 공개 검사를 수행했다. 질문 임베딩과 순위 결정 함수는 항상 같은 벡터와 후보 두 권을 반환하도록 대체했다.

각 버전에서 Spring과 DB를 계속 실행하면서 AI 프로세스만 세 번 재시작했다. 매번 Spring의 갈피 상태가 사용 가능해지면 인증된 `POST /api/ai/jobs`로 ‘번아웃이 올 때 읽을 만한 책을 추천해줘’를 접수하고 같은 작업 ID를 완료까지 조회했다. 다음 요청도 같은 질문으로 새 작업을 접수했다. 아래 시간의 단위는 초다.

## 후보 준비 시간

두 버전의 동일한 검색 함수에 Python 3.12의 줄 단위 타이머를 연결해 모듈 로딩, 의도 분석, 후보 필터링, 벡터 점수 계산과 정렬, 비교 대상 제외를 나눠 측정했다. 수정 전에는 첫 검색마다 제목 비교 모듈이 NumPy를 로드했고, 독립 프로파일에서 모듈 로딩 3.77초 중 NumPy에 3.15초가 걸렸다. 수정 후에는 실제로 기준 작가의 벡터를 계산할 때 해당 의존성을 불러온다. 수정 후 갈피 추천 6건 모두 NumPy 로딩 없이 완료됐다.

| 첫 요청 중앙값 | 수정 전 | 수정 후 |
|---|---:|---:|
| 후보 준비 전체 | 1.93초 | 0.36초 |
| 그중 검색 모듈 로딩 | 1.63초 | 0.03초 |
| 그중 벡터 점수 계산·정렬 | 0.17초 | 0.23초 |
| 인덱스 준비 | 1.73초 | 1.45초 |
| AI 처리 전체 | 3.70초 | 1.82초 |
| 접수부터 결과 확인 | 4.95초 | 2.63초 |
| 재시작부터 사용 가능 | 24.10초 | 20.20초 |
| 재시작부터 첫 결과 | 28.84초 | 23.56초 |

수정 전후 12개 작업이 모두 같은 순서로 도서 2권을 반환했다. 접수 후 30초 기준은 이 환경에서 수정 전후 모두 3회 통과했다. 운영에서 관측한 46.28초의 전체 지연과 외부 모델 응답 시간은 이번 실험의 측정값으로 환산할 수 없다. 샘플에는 새 Spring과 AI가 함께 올라올 때의 호스트 부하도 포함되지 않는다.

기존 AI 로그의 `candidate_ms` 안에서 모듈 로딩은 `candidate_import_ms`, 벡터 점수 계산과 정렬은 `vector_score_ms`로 확인할 수 있다. 두 값 모두 질문과 도서 원문을 기록하지 않는다. 운영 배포 전에는 검색 소스가 바뀌어 생성된 새 코퍼스 식별자로 실제 품질 평가를 두 차례 통과하고 Spring과 AI의 릴리스 설정을 함께 전환해야 한다. [코퍼스 검증 절차](../../../deploy/CORPUS_TRANSITION.md)

새 프로세스에서 제목 비교 필터를 불러와 같은 동작을 확인하려면 `BookAppAI` 디렉터리에서 `python -m pytest -q tests/test_reference_search.py`를 실행한다. 이 테스트는 비교 대상 책의 제외와 작가 유사도에 사용하는 기준 벡터 계산을 함께 확인한다.

## 첫 접수와 결과 조회 · PR #44 후속 검증

운영에서 첫 제출은 QA 클라이언트의 20초 대기를 넘겼다. QA 클라이언트가 같은 요청 키로 다시 제출했다. Spring은 첫 요청을 12.50초, 두 번째 요청을 2.60초에 처리해 두 요청 모두에 202를 반환했고 DB에 등록된 작업은 한 건이었다. 결과 조회 503 두 건은 3.13초와 3.29초에 끝났다. Spring의 릴리스 확인 기한은 3초다. 운영 로그만으로 첫 제출이 지연된 각 단계나 당시 인증서 읽기 시간을 확정할 수는 없다.

**로컬 재현.** 배포된 커밋 `ff27e84`의 검색 경로, 합성 코퍼스 176권, PostgreSQL·Redis·Spring·FastAPI·내부 라우터를 사용했다. Spring에는 구간별 시각을 기록하는 로컬 로그를 추가했다. 외부 임베딩과 순위 모델 응답은 각각 1초 뒤 반환하도록 고정했다. HTTP 클라이언트 생성과 TLS 신뢰 저장소 읽기는 실제 코드로 실행했다. 인증서 최초 읽기가 4초 느려지는 조건을 양쪽에 똑같이 적용했다. 이 값은 장애 재현용이며 운영에서 측정한 인증서 시간은 없다.

수정 전 실제 작업 API는 첫 제출을 3.87초에 접수했다. Spring의 로컬 구간 계측에서 릴리스 확인은 15ms, Redis 사용량 제한 처리는 857ms, 그 뒤 서비스 진입까지 517ms였다. 대기열 크기 확인은 490ms, 새 작업 저장·커밋은 198ms였다. Spring은 결과를 조회할 때 AI 서버에 갈피 공개 상태를 확인한다. 이 확인이 3초 안에 끝나지 않아 Spring이 상태 조회 두 건에 503을 반환했다. 같은 지연을 독립된 파이썬 프로세스에서 적용한 시험에서는 이벤트 루프가 가장 오래 멈춘 시간이 4.55초에서 0.34초로 줄었다.

**수정.** AI 서버는 검색을 열기 전에 HTTPX가 서버 인증서를 확인하는 데 쓰는 신뢰 저장소를 별도 스레드에서 읽어 두고 재사용한다. 임베딩과 Gemini·Groq 순위 모델의 HTTP 클라이언트 구성도 이벤트 루프 밖에서 실행한다. 웹과 앱은 작업 ID를 받는 POST에 30초를 허용한다. 기존 10초 제한으로는 운영에서 관측한 첫 서버 응답을 기다릴 수 없었다.

**화면 검증.** 각 회차에 Spring과 AI를 새로 기동하고 갈피 이용 가능 응답을 확인했다. 모바일 크기 Chrome에서 같은 번아웃 질문을 검색했다. 실제 버튼 클릭부터 첫 추천 제목이 보일 때까지 측정했다. 세 번 모두 POST 한 번으로 접수됐고 같은 합성 도서 두 권이 표시됐다.

| 재시작 | 클릭부터 접수 응답 | 클릭부터 첫 책 표시 | 작업 상태 조회 |
|---|---:|---:|---|
| 1 | 2.68초 | 12.17초 | 3회 모두 200 |
| 2 | 4.16초 | 12.78초 | 3회 모두 200 |
| 3 | 3.22초 | 11.63초 | 3회 모두 200 |

세 회의 화면 표시 평균은 12.19초였다. 별도 시험에서는 이미 접수된 POST의 브라우저 응답 전달만 12.5초 보류했다. 재제출 없이 13.25초에 작업 ID를 받았고 14.22초에 결과가 보였다. 서버를 기동하는 데 걸린 시간은 클릭 이후 측정에서 제외했다. 운영의 모델 지연과 단일 호스트의 메모리 압력은 다음 운영 배포에서 별도로 측정한다. 순위 모델 호출 코드가 코퍼스 식별자에 포함되므로 운영 배포 전에 실제 176개 판본으로 새 식별자에 대한 품질 평가를 두 차례 통과해야 한다.

회귀 검증은 `BookAppAI`에서 `python -m pytest -q tests/test_model_http.py`, `BookAppFront`에서 `node --test tests/search-api-errors.test.cjs`로 실행한다.
