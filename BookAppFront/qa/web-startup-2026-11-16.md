# Safari 첫 진입 표시 개선 (2026-11-16)

## 기준점

기존 배포·웹 접근 통제·탭 UI 변경은 `7d18881`로 `feat/mobile-web-beta`에 커밋·푸시했다. 시작 화면 개선은 별도 `fix/web-startup-rendering` 브랜치에서 진행한다.

## 재현과 원인

iPhone 16 Pro / iOS 18.2 시뮬레이터의 실제 Safari에서 로컬 정적 빌드를 열었다. 최초 방문 캐시 영향을 피하려고 조건별로 다른 localhost 포트를 사용했고, TTF·OTF 응답만 10초 늦췄다. 로그인 경로를 사용해 AI/API 처리 시간을 측정에서 분리했다. 진단용 HTML에만 performance paint entry와 root 존재 여부를 수집하는 코드를 넣었다. 이 진단 코드는 배포하지 않는다.

| 조건 | Safari 첫 콘텐츠 표시(FCP) | 관측 |
| --- | --- | --- |
| 기존 `auto` + Expo 폰트 preload | 10,588ms | 화면 구조가 먼저 생겼지만 폰트 준비까지 표시 지연 |
| `swap`만 적용, preload 유지 | 10,394ms | 지연 유지 |
| `swap` + preload 제거 실험 | 1,106ms | 폰트가 loading인 동안 화면 표시 |
| 최종 빌드·HTML 준비 스크립트 적용 | 1,335ms | 폰트 10초 지연 중 화면 먼저 표시 |

Chromium에서는 기존 구성도 같은 지연 조건에서 빠르게 표시됐다. Safari와 동일한 증상이라고 가정하지 않고 실제 Safari에서 조건을 나눠 비교했다. 수치는 통제된 로컬 재현 결과이며 일반 사용자 환경의 보장 응답시간이 아니다.

## 변경

- 시작 폰트는 `FontDisplay.SWAP`으로 지정해 기본 글꼴로 먼저 읽을 수 있도록 했다.
- 웹은 폰트 완료 여부로 루트 화면을 숨기지 않는다. 네이티브는 기존 폰트 대기를 유지하되 오류가 나면 시스템 글꼴로 진입할 수 있도록 했다.
- 정적 빌드 준비 단계가 모든 HTML 경로에서 `rel=preload, as=font` 링크만 제거한다. `@font-face`와 이미지 preload는 보존한다. 현재 빌드에서는 13개 경로의 39개 폰트 preload를 제거한다.
- 배포 검증기가 `font-display: swap`과 폰트 preload 부재를 확인한다. 이후 원래 설정이 들어오면 CI/배포 빌드가 실패한다.
- 전용 글꼴은 백그라운드에서 계속 다운로드하며 준비 후 교체된다. 원본 폰트 파일의 크기와 글리프 범위는 유지했다.

## 검증

- TypeScript, ESLint 통과.
- 프런트 테스트 5개 통과. 중첩 HTML 처리, 이미지 preload·font-face 보존, 의존성 자산 복사, 반복 실행과 잘못된 폰트 설정 거부를 포함한다.
- 실제 공개 API 주소로 Expo 정적 export와 HTML 준비·배포 검증 통과.
- 폰트 응답이 모두 503인 빌드에서도 Chromium 로그인 화면과 입력 필드가 유지됐고, 입력 및 빈 비밀번호 안내가 작동했다.
- 이 변경의 성능 측정은 첫 콘텐츠 표시를 다룬다. API 검색 처리 시간이나 네이티브 앱의 첫 실행 속도를 측정한 것은 아니다.
